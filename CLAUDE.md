# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Source-to-Story: turns a book (PDF) or article into a 16:9 long-form video through three stages with a human checkpoint each: Phase 1 `story/` (source to story candidates), Phase 2 `story2/` (story to video plan), Phase 3 `story3/` (plan to voice, pictures, graphics, ffmpeg draft video). `shorts/` (Phase 4) makes 30-second 9:16 shorts: the image model (Qwen Image) draws a start picture per shot, Wan 2.2 models make every moving picture; plan and status in [docs/PLAN_shorts.md](docs/PLAN_shorts.md). `legacy/` is the old news-podcast generator, not served; leave it alone.

The active quality plan (audit, tasks, status of each) is [docs/TASKS_quality_overhaul.md](docs/TASKS_quality_overhaul.md): read it before changing narration, scenes or prompts, and tick tasks there as they land. Read [docs/RUN_LOG.md](docs/RUN_LOG.md) for what the latest end-to-end runs found and fixed, and [docs/APP_GUIDE.md](docs/APP_GUIDE.md) first (owner rules, measured model facts, invariants, plan-screen flow) and [docs/ROADMAP.md](docs/ROADMAP.md) for what remains.

## Commands

Windows; the app runs from `.venv`.

```
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env                       # TRIPFICK_API_KEY, APP_PASSWORD
.venv\Scripts\python.exe main.py             # http://127.0.0.1:8905
start.bat                                    # watch.py: runs app, auto-pulls origin/master, restarts when idle or on crash
.venv\Scripts\python.exe -m pytest tests     # all tests, mocked models
.venv\Scripts\python.exe -m pytest tests/test_phase3i.py -k name    # single test
set LIVE_LLM=1 && .venv\Scripts\python.exe -m pytest -k live        # optional real-model tests
```

No linter or build step configured. `static/plan.js` is served from disk uncached, so frontend-only changes need no restart; Python changes do. Never restart while a generation job is running (watch.py waits for this).

## Architecture

- `main.py` mounts four FastAPI routers: `story/api.py` (`/api`), `story2/api.py` (`/api/plans`), `story3/api.py` (`/api/media`), `shorts/api.py` (`/api/shorts`). UI is plain static files (`static/index.html`, `plan.js`), no framework.
- All models sit behind one local OpenAI-compatible gateway (default `127.0.0.1:8810/v1`): chat/vision (Gemma), voice (Veena `agastya` by default, Svara `hi_male` selectable; `story2/voices.py`), images (Qwen Image 2.1 is the default; FLUX.2 Klein and every other image model the gateway lists are selectable per scene). Gateway allows one concurrent request per key, so `story2/jobs.py` runs one background job at a time and refuses a second.
- Data in gitignored `data/`: SQLite `story.db` (Phase 1 tables, Phase 2 `plans/segments/scenes/assets/plan_revisions`, Phase 3 `media`), plus sources, exports, previews, media files.
- Phase 3 `media` rows are numbered attempts, never overwritten; approving one un-approves siblings (`story3/store.py`).
- `story3/auto.py` is the "Auto-run" job that chains every unfinished step; keep it in sync when adding a step (and with the step order in `static/plan.js`: the order is blueprint, narration, characters, storyboard, references, prompts, repeats, approve, export, voice, pictures, graphics, video, thumbnail).
- `story2/director.py` plans the whole film as shots (emotion, place, size, angle, camera move per segment) before any scene is drawn; `make_storyboard` calls it when no current plan exists. Each scene names the shot it follows (`scene.data.direction`), the shot's size and angle are written into `composition`, and `story3/video.py` takes the camera move from `direction.move`. Anything planned must be wired the same way: field in the scene, text in the Qwen prompt (`imgprompts.compile_qwen`, camera first), consumer in the video build.
- Tests use fake models/gateways (`tests/fakellm.py`, `tests/conftest.py`).

## Shorts (Phase 4, `shorts/`)

- Start pictures: image mode `qwen` (default) has the planner write a `still` prompt per shot (`shot.still`, editable) and `shorts/stills.py` draws it with the gateway image model (`settings.image_model`, default `qwen-image-2.1`, 720x1280) through `/images/generations`; the person looks at the storyboard (contact sheet, redo/edit/upload per shot) before any video is made. Uploaded pictures win; `wan` mode = no stills (Wan decides, the old behaviour). `pipelines.keyframes_on` says whether a short has the start-picture step (keyframe pipeline always; quick unless mode `wan`).
- Three pipelines, chosen by the Wan model: `quick` (5B, from the start picture, or text in mode `wan`), `keyframe` (a start picture per shot, checked by a person, then each animated with the 14B image-to-video model at full quality), `remix` (Animate: a YouTube video's motion on the user's character). Speed LoRA is off everywhere ("always final"). Clip requests are built only in `shorts/pipelines.py` (and `remix.request`); the one gateway client is `shorts/wan.py`, also used by `story3/clips.py`.
- Owner rule: **no shot is on screen longer than 3.0 seconds** and the short is exactly 30 s (900 frames at 30 fps). `shorts/timeline.py` fits the voice into 30 s and gives every shot whole output frames; `shorts/checks.py` blocks Make on a longer shot; `planner.fit_shots` rewrites a beat's shots when the real voice runs long. Clips are generated at the next 4n+1 frames and trimmed in `stitch.py`.
- Script (`shorts/script.py`, setting `script_engine` = `room`, default): the writers' room writes the narration before the look is planned: story bible, retention map (a job per beat, seconds to words in code), one draft call per beat (dialogue, a voice tag per sentence), then a punch-up critic (score 1 to 10, up to two rounds, a rewrite that breaks the beat ids or word budget is ignored). The old one-call plan is `script_engine=single` and the fallback when the room fails. No content limits in the script prompts (a person reviews). Every sentence starts `neutral` (the producer or the voice-direction step sets emotions later). At 30 s the narration is 64 to 96 words (asked 80 to 90); the voice may speed up to x1.35 (`timeline.TEMPO_MAX`) to land on the length. A scene or the whole script can be rewritten on the plan screen (`POST /api/shorts/{id}/rewrite`, `planner.rewrite_beat` with the producer's instruction, `planner.rewrite_script`): same beats, same shots, voice of a changed beat made again. Length is `settings.target_s`, 5 to 180 seconds, default 30 (`models.MIN_TARGET_S`, `MAX_TARGET_S`); word budget and beat count scale in `planner.word_limits` and `planner.beat_range`.
- Narration address and flow: Hindi/Hinglish narration speaks to the viewer as **aap** (`languages.ADDRESS_AAP`, setting `address`=`tu` opts out); `script.hard_problems` + `script.repair` rewrite any beat left with Latin-script Hindi or tu/tum after the punch-up. Map `cliff`s are optional and thinned in code (`fit_map`: at most one beat in three, never the last); a beat ends on a statement unless it has a cliff.
- Upload text (`shorts/publish.py`, task `p4_publish`, `short["publish"]`, `POST /{id}/publish`): a search-friendly YouTube title (<=70), hook-first description with one hashtag line, hashtags and tags, written after the final video by Auto-run and copyable on the short page; `view` marks it stale when the narration changed.
- Light by default: `looks.of` brightens every style except `looks.DARK_STYLES` (noir, cyberpunk) and adds `looks.LIGHT`; the plan, subject and still-writer prompts say bright daylight unless the beat's feeling or words are dark.
- Short Ideas (`shorts/ideas.py`, `shorts/discover.py`, `static/ideas.js`): generate/rate/condition run as background jobs (`jobs` key `ideas`; `GET /ideas/run` for progress and new idea ids; the screen polls, so leaving it loses nothing). A batch = web signals (gateway `web_search` tool, called by our code; `discover.signals`) -> ideas that cite their sources -> `dedup` (word overlap, then a chat-model judge; any earlier idea of any status; duplicates are auto-rejected with `reject_reason`/`dup_of`) -> rate -> auto-approve at `approve_min` (7.8). Config (saved on the server, `/ideas/config`): styles ticked for ideas (`pick_style`: only those, rotating), Autopilot master switch (`autopilot`, OFF by default) plus `auto_generate` (hourly, 5 ideas), `auto_approve`, `auto_condition`, `autorun` = make a short every `make_every_h` (2) at `min_score`, `review_cap` (pause making while that many finished shorts are not marked reviewed), `pending_cap`. `api.conductor_tick` (every 30 s from `main.py`) starts at most one job and none while any job runs (the key serves one request at a time); schedule times live in the config row. Web signals also read the date from the `now` tool and the start of the first result of four queries with `fetch_url` (`discover.py`). Bright styles are ticked by default (`ideas.BRIGHT_STYLES`) and the brief's visual direction is forced to name an allowed style. The screen has a board of the three stages (approved / conditioned / queued, with Condition now / Make now per idea via `POST /ideas/autopilot/run` `idea_id`), and queued cards show the short's YouTube upload text. Conditioning hands the script room the concept only (refined hook as the angle, key facts, visual direction, tone); arc, beats, feelings and the opening line belong to the room (bible, map, drafts), so `_queue_idea` sends no arc and the conditioning prompt asks for none (older briefs keep their stored fields, the card still shows them). Idea status flow: pending, approved, conditioned, queued (short being made), done (the short has its final video; `api._sync_done` moves it on every list/board/tick, no review click; "reviewed" only feeds `review_cap`); `approved_at`/`conditioned_at`/`done_at` give "waiting since", and `ideas.order` (score desc, oldest first) is the one order the pickers and the board's `rank`/`hold` use. A brief that fails twice is skipped by the autopilot (`cond_fails`, kept in the database). `story/llm.py` waits (up to 15 min) on a `concurrency_limit` 429 instead of failing.
- Picture prompts (`shorts/stillwriter.py`, task `p4_still`): after the shots of a beat exist, a separate Gemma call writes every shot's `still` for Qwen (exact counts, where each part is, positive words only, no filler adjectives, proves the narration line) and `must_show` (2 to 4 facts to check on the picture); code sends a vague amount, a negative or filler back. A failed call keeps the shot planner's still. `stills.prompt` puts the still first, then each look once (main character not repeated as a subject, a place subject becomes the setting), the style and the keep-out; no camera line. Redo: `POST /api/shorts/{id}/pictures/write` (`shot_id` + `instruction`, or all).
- Motion prompts (`shorts/motionwriter.py`, task `p4_move`, `shot.move`): written after the timeline exists (seconds known), per beat, from the final start-picture prompt, the narration line and the neighbours' moves. Only what moves (subject action, camera in plain words, one motion of the surroundings), never looks or style; code sends back negatives, looks words and a missing camera. `pipelines.compose(with_picture=True)` sends `move` + `HOLD` only (no character, place, look, or camera line) and the i2v/5B-with-picture requests use `NEGATIVE_MOVE`; without a written `move` it falls back to the planner's prompt + camera (no look). Avatar and reference-video shots are skipped. Redo: `POST /api/shorts/{id}/motion/write`; rewriting a picture prompt also rewrites that shot's motion.
- Voice is made per beat before any clip (shot lengths come from the real voice, `planner.sync_timing`). Voice, keyframe and clip validity are hashes of their inputs (`store.input_hash`, `pipelines.req_hash`, which leaves the seed out), like the long-form media.
- Clips, keyframes, voice and the final video are `media` rows with `plan_id` = the short's id (kinds `short_key`, `short_clip`, `short_voice`, `short_final`). A running attempt stores the gateway's job id; `clips._adopt` resumes it after a restart.
- Talking avatars (`shorts/avatar.py`, plan in [docs/PLAN_avatar.md](docs/PLAN_avatar.md)): a shot flagged `avatar` (checkbox on the shot card, needs a library character in the shot and the beat's voice) starts from its storyboard picture, which `stills` frames front-on (`AVATAR_FRAMING`), and that picture speaks the shot's slice of the beat's voice through InfiniteTalk (`models.TALK` = `infinitetalk-14b`, 25 fps, 4-step speed LoRA). One request per shot (at most 3.0 s), request in `pipelines.avatar_request`, clip plan branch in `clips.clip_plan`, clip hash includes the voice take, so a new voice makes it old. Wan S2V is deliberately not used (too slow, owner decision). The model is installed in the gateway repo `D:\MiniMaxH3` (workflow `wan21_infinitetalk` in `video_wan14.py`, weights in `C:\ModelWeights\InfiniteTalk`).
- Optional 2K (`shorts/upscale.py`, setting `upscale` = `2k`, not for remix): the gateway upscaler (`POST /v1/video/upscale`, model `video-upscale`, max 300 frames and 2560x1440 pixels, so never the whole 900-frame short) upscales each chosen clip on its own to `data/media/<short>/up/<clip id>-2k.mp4` (files, no media rows; regenerable). It is an auto-run step before "Put the short together" (`auto.run`, the Final button does it too); `stitch.build` then cuts those files at 1440x2560 (`models.out_size`) and refuses while any is missing. Final hash and `changed_since` include the setting. Captions keep a 1080x1920 ASS canvas, which scales.
- Remix: the motion guide is a YouTube or Instagram link (`HOSTS`; optional `data/cookies.txt` for logins) or an uploaded file, and the character is a library character and look (`remix.character`, `remix.picture`; a new character version makes the clip old) or an uploaded picture. The video is only the motion guide; it stays under `data/media/<short>/remix/`, is never exported or uploaded, and two rights boxes must be ticked before Make. Animate does not keep the video's own background (character and background come from the picture and the prompt). With a library character the prompt is written for you (`remix.auto_prompt`: its details, a chosen look's outfit instead of the outfit slots, and an optional library place `remix.place_id` as "Background:"); the person's own text, when there is any, wins (`remix.effective_prompt`); a new place or character version makes the clip old.
- `python -m shorts.probe` measures the gateway's Wan models and writes `data/shorts_probe/timings.json`, which the time estimates read. Run it first on a new gateway.
- Tests: `tests/test_shorts.py` with `tests/shorts_fakes.py` (mock video gateway, fake chat, tone voice, tiny ffmpeg clips).

## Character Studio (`characters/`, plan in [docs/PLAN_characters.md](docs/PLAN_characters.md), tasks in [docs/TASKS_characters.md](docs/TASKS_characters.md))

- A library of reusable people and places (`chars` table, router `/api/characters`, `static/characters.js`). Pictures are `media` rows with `plan_id` = the character id (kinds `char_gen`, `char_sheet`). Canon = the approved portrait and full-body (places: the establishing view); canon change bumps `version`; `store.identity_hash` (slots + render + photo) marks older pictures.
- Image requests are built only in `characters/requests.py`: draw from the slot paragraph (`describe`), sheet views by edit from the canon (up to 2 references, instruction names pictures by position, keep list). Studio jobs use the same one-job lock (`story2/jobs.py`).
- The render style, image model and LoRA set (`characters/render.py`, default `photoreal` + `purelens-realism` 0.7 + trigger `p3r4l4ns`) are chosen at creation and LOCKED once canon exists: a different LoRA draws a different person, and an edit keeps the look of its source picture (C0 findings in docs/RUN_LOG.md). To try another look, duplicate.
- `python -m characters.probe` measures the gateway's image models for characters (groups base, edit, multi, drift, flux, tryon, lora, lorafield); it waits while the app holds the gateway.
- Edits (`characters/edits.py`): free edit of any picture (presets or the person's sentence, up to two extra references), try-on from a garment picture (`characters/wardrobe.py`; a garment photo worn by a model gets the copy-only-the-clothing wording and can be turned into a person-free flat lay first), the character in a place (three references), looks, expression grid. `characters/check.py` is the strict feature-by-feature identity check (8 features, pass at 7).
- Shorts cast: `settings.cast` (up to two library characters + `place_id`) makes `shorts/cast.py` feed the planner and build start pictures by edit from the canon pictures (`stills.build`); `fix_keyframe` changes one thing in a start picture; a new canon version makes cast pictures old.
- Declared facts: ethnicity, gender (male or female), age, skin tone and build are decided by the person (a place: its region) and forced into the slots in code; the chat model (`studio.SLOTS_SYSTEM`) writes the rest as Instagram-reel-worthy, culturally authentic, realistic work and is refused until all are declared. Every field has a preset list (`characters/choices.py`) and accepts free text; chosen details are kept when the model fills the empty ones.
- Qwen draws every word literally, so the first pictures are a clean human: `requests.visible_slots` leaves out what the frame cannot show (trousers and footwear in portraits, hair length beyond the shoulders) and all accessories (added later by accessory edit or look); no mood line; 35 steps (`requests.STEPS`). Shorts close-ups do the same to the character paragraph (`stills.framed_character`).
- Styling `glamour` (`characters/choices.py` STYLING and OUTFITS, `store.glamour_problem`): fitted, softly revealing, tasteful and always clothed; only for invented people with a declared age of 21 or more, never from a photo; adds `requests.GLAMOUR_LINE` and the chat model's `GLAMOUR_RULES`; presets never contain nudity or lingerie.
- Tests: `tests/test_characters.py`, `tests/test_characters_edit.py`, `tests/test_characters_declared.py`, `tests/test_shorts_cast.py` with `tests/characters_fakes.py`.

## YouTube analytics (`youtube/`, `static/youtube.js`, page `#/youtube`)

- Read-only Google OAuth (scopes `youtube.readonly`, `yt-analytics.readonly`); `.env` holds `YT_CLIENT_ID`, `YT_CLIENT_SECRET`, `YT_REDIRECT_URI` (must be https, or localhost, and be the address the app is opened on, because the login cookie has to come back with the callback). Refresh token in table `yt_auth`; `state` is signed and expires (`oauth.make_state`). Tests set `oauth.TRANSPORT` to a mock transport.
- `sync.run`: channel -> uploads (Data API, newest 200) -> `yt_videos`; daily numbers per video (Analytics API, `dimensions=day`, 60 newest videos from the last 120 days, linked first) -> `yt_stats`. Background loop `sync.forever` (main.py) syncs every 3 h while connected; "Sync now" on the page.
- Linking video -> short -> idea (`yt_links`): by title (>= 0.92 similarity to the short's upload title or title, video published after the short was made) or by hand (`POST /api/youtube/link`, a hand link is never replaced). Windows of views (first 2/7/28 days) count as complete two days after the window ends; "What works" averages the first 7 days by score band, style, tone and mechanism. Idea cards and the Done column show the channel's views (`yt`). Tests: `tests/test_youtube.py`.

## Feedback loop (`feedback/`, `static/learn.js`, YouTube page tab "Learn", plan in [docs/PLAN_feedback_loop.md](docs/PLAN_feedback_loop.md), tasks in [docs/TASKS_feedback_loop.md](docs/TASKS_feedback_loop.md))

- Learning window: only videos published on or after `outcomes.learn_from()` (default 1 Nov 2026 IST, owner rule; kv `learn_from`, `POST /api/feedback/learn-from`) count anywhere in the loop (`outcomes.in_window`). The Learn tab has a collapsible "How this page works" help (`help()` in `static/learn.js`): keep it in sync when the tab changes. A Playbook is also drafted weekly (`generate.due_for_draft`) when something new was graded.
- Grades: `outcomes.grade` scores every channel short 0-100 against the channel's own medians (reach 40, retention 30, engagement 15, growth 15; each index `100*i/(i+1)`; missing parts left out = `partial`; 7-day window needed, `early_grade` from the 2-day one). Labels winner/flop by quarter once 8 are graded. `idea_outcomes` holds the features frozen when the short is queued (`_queue_idea` -> `features.freeze`) and the grade; older channel videos join the sample through title-only features and `yt_video_tags` territories.
- `insights.lifts` (shrunk by `n/(n+4)`, groups under 3 hidden), `calibration` (rank correlation of the idea score with the grade, threshold advice with an Apply button), `experiments` (choices labelled `exploit`/`explore`/`idea`/`rotation`/`model`).
- Playbook memory (`playbook.ledger`, `merge`, `judge`): a draft is the lessons in force carried over plus the delta. Each item has `memory.state` (new / reinforced / replaces / known / carried); repeats are left out, `NothingNew` makes no draft, upload-time lessons are dropped (`off_topic`), a draft written before the learning start date is `stale` (flagged on the page). Each idea freezes the Playbook version in use (`features.playbook`).
- Only an APPROVED Playbook (`playbooks` table; `playbook.draft` writes drafts, the owner approves on the page) steers anything, and only while `use_playbook` is on (`playbook.enabled`): `ideas.feedback_extra` (learnings + territory plan in the generation prompt), `bandit` (territory plan, `ideas.style_choice` fallback, tone arm on an explore roll; explore share `explore` 0.30-0.40), rating anchors, the title note (`publish.learnings`) and script note (`script._source`). Items carry scope + evidence video ids (code drops uncited ones); pinned principles apply whenever the switch is on. Drafts are never used.
- Idea sources: `generate.sequels` (winners at 3x reach or more, origin `sequel:<idea>`), `generate.comment_ideas` (top public comments in `yt_comments`, origin `comment:<video>`; comments are fenced as data). The autopilot step `auto_feedback` (`api._start_feedback`, daily) grades, tags, drafts a Playbook when enough new videos were graded, and proposes ideas; it never approves. Tests: `tests/test_feedback.py`.

## Story simulator (`sim/`, `static/sim.js`, page `#/sim`, nav "Stories", plan in [docs/PLAN_simulation.md](docs/PLAN_simulation.md), tasks in [docs/TASKS_simulation.md](docs/TASKS_simulation.md))

- An idea becomes a world card, a cast (characters and places), **trackers** and rules (`sim/seed.py`, four calls so each can be redone); then chapters of about 350 words grow one at a time. The engine knows no genre: what a story keeps count of is data (tracker kinds `items`, `meter`, `clock`, `relation`, `location`, `knowledge`, `flag`; `sim/state.py`). A test greps the engine for genre words, and a courtroom story runs on the same code as the supermarket one.
- One chapter (`sim/engine.run_chapter`) = gather (due instructions) -> plan (`sm_plan`) -> optional minds (`deep`) -> resolve (dice in code, `sim/dice.py`) -> delta (`sm_delta` proposes operations, `state.apply_ops` decides which are real) -> write (`sm_write`, word range checked) -> referee (hard/world rules and continuity; one rewrite, then flagged `rule_break`) -> archive (summary, fact cards, open threads, 3 to 4 options). Every stage stores its result on the chapter row (`flags.done`), so "Retry from this step" continues; a chapter left `writing` by a stopped server is marked `failed` at start-up (`store.repair`). Old chapters are never rewritten: a rewrite or reroll makes a sibling (branch).
- State rules (code, not the model): an item appears only from a known place that holds it (word match against the world card's `exists` text) or from parts used up in the same step; the dead cannot act; meter changes are limited to half the range; clocks go forward unless a reason is given; a death needs a failed roll, a fired instruction or a full clock when dice are on. Refused operations are kept in `chapter.delta.dropped` and shown on the page.
- Instructions (directives): timing `next`, `in` N chapters, `when` (a tracker test or a free-text condition judged by `sm_condition`), `story_time`. Firing is stored on chapters (`fired`), pending = not cancelled and not fired on the current line, so branches never share it. Owner text is always fenced `<owner>..</owner>` in prompts.
- Memory (`sim/memory.py`): prompts are built only there, from the current line: world, rules (R1..), state, people, story so far (roll-up every 12 summaries merging 8), recent summaries, last chapter's ending, matched fact cards, open threads (T1..). Over budget, the lowest-priority parts are dropped whole (facts, older summaries, other people), recorded in `flags.trimmed`.
- Pictures (`sim/paint.py`): cinematic painted style only (constants `STYLE`, `KEEP_OUT`), drawn from text; one reference painting per person and place (`sim_ref`), panels (`sim_panel`, 3 to 5 per chapter from `sm_panels`) are edits from those references and fall back to text. Captions are lettered by code. Panel/reference hashes make pictures `old` when a look, the plan, style or model changes. Pictures never use Character Studio (a test checks). Image jobs wait behind text jobs (one-job lock).
- Thinking (`sim/think.py`): the gateway thinks by default (`reasoning_content`, counted in `max_tokens`; `enable_thinking`/`thinking_budget` per request, docs at llm.tripfick.com/docs). A per-task budget table (plan, delta, referee 1.5k-2k; write 512; roll-up, minds, items 0) is merged under the owner's sampling overrides by `engine._json`; the story setting `thinking` = off / balanced / deep scales it, and the job runner sets it for the job (`think.mode`). Room: every sim call asks for `max_tokens` 16000 (the app default is 10000; thinking and answer share it) and a 600 s timeout (`think.room`); a reply cut off at the limit is asked once more with thinking off and 24000 tokens (`engine._json`) before the step fails.
- Content freedom (`sim/content.py`, story setting `content` = clean / mature / unfiltered, default unfiltered because the owner's model is unrestricted): its text is the `CONTENT` block of every chapter packet and of the setup calls; the planner, writer and option writer are told to allow strong language, cruelty and crime when it does; the referee never counts them as violations (only rules, state and continuity). Mild sexual content between adults (suggestive, scene closed before explicit detail; never anyone under 18) is allowed at `mature` and `unfiltered`. Consequences stay in the world through rules and dice.
- Things (`sim/things.py`, plan in [docs/PLAN_discoveries.md](docs/PLAN_discoveries.md), tasks in [docs/TASKS_discoveries.md](docs/TASKS_discoveries.md)): a thing in an `items` tracker has `props` (condition, uses, size, tags), `origin`, `bound_to`; the state also carries `world_add` (finds of this line: items, places, clues) and `recipes`; people have `skills` and a carrying limit (setting `carry_limit`, per-person `carry`, 0 = none). New operations `discover`, `craft`, `item_give`, `item_take`, `item_use`, `item_change`, `skill_learn`; the model reasons (plan risk `kind` and `craft{makes,parts,tools,skill,reasoning}`), code decides: a find needs a resolved search/learn act with tier success or better (partial = damaged), an instruction that names it, or text already in the world; a make needs held parts (used up) and tools (kept) and a rolled make act (skill +2, improvised target +2, right tool +1, known recipe one step easier; fail loses half the parts); a give the receiver may refuse needs a rolled persuade, a take a rolled take; `bound_to` things cannot move except by an instruction; caps 2 finds, 2 makes, 1 skill per chapter. Every change records its way back (`applied[].undo`); `POST /{id}/chapters/{cid}/undo` and `POST /{id}/things` (the Things tab) use `things.edit`. Instruction kinds `grant`, `take`, `unbind` are carried out by code (`engine._instruction_ops`, forced ops). Thinking steps up 1.5x for plan and delta when the player's action is about making, finding or learning (`think.boost`). Rule group `craft` and the world card's `craft` line say what can be made here; templates carry both.
- Drama engine (plan in [docs/PLAN_drama.md](docs/PLAN_drama.md), tasks in [docs/TASKS_drama.md](docs/TASKS_drama.md)): `sim/health.py` computes story health from the chapters with no model call (dice record, costs from state differences, tension 0-10 per chapter, spotlight, goals/fears/secrets not surfaced, open-thread age, ending class hook/decision/reveal/question/menu/plain, repeated words, option repeats and errands, clocks, plain verdicts) and the API returns it as `health` (Health card on the Story tab). `sim/drama.py` is the director: story setting `length` (0 = open-ended six-chapter waves, else one arc: setup, rising, midpoint, crisis, climax, resolution) gives the plan prompt an ARC AND PACING block with a tension target; a NEGLECTED block (people away 3+ chapters, goals/fears/secrets and threads unused) that the plan must touch from chapter 4 on; the plan field `opposition` (required; shown to the delta and the writer); `calibrate` makes the easiest planned act one step harder after two free chapters (easier after punishing ones); `ensure_cost` adds a cost (the actor's or group's meter, else the first clock) when a failed or partial act left no real cost, listed as op `cost`; auto-run stops at the planned length. The writer is sent back when a chapter ends on a menu of routes; options carry `cost`, risk words are stripped from the hint, repeats are dropped; setup adds relation trackers for pairs the cast cards relate (`seed._relation_trackers`). The world card has a `goal` line ("THE STORY IS ABOUT") that the planner and options must serve.
- Everything model-related runs as the one background job (`sim/jobs.py` over `story2/jobs.py`, keyed by story id; `GET /api/sim/{id}/run` is polled by the page, which resumes watching on load). Delete (`store.delete_project`) removes every `sim_*` row, the media rows and the folder; the storage page knows `sm-` ids. Export: Markdown, zip with pictures in order, chapter JSON (the contract of a later chapter-to-video step), and importable story files (`sim/portable.py`). Tests: `tests/test_sim.py`, `test_sim_api.py`, `test_sim_paint.py`, `test_sim_complete.py` with `tests/sim_fakes.py`; `python -m sim.spike` runs two unlike stories on the real gateway (a chapter takes about 5 minutes on the local model).

## Storage clean-up (`admin/`, Settings page)

- On demand only, never automatic. `admin/storage.py` measures `data/media/<id>/` per long-form plan (`pl-`), short (`sh-`), character (`ch-`) and the wardrobe, and clears one project by `folders`, `older` (keep the approved or newest finished attempt of each key, remove the rest and failed ones; skipped for characters) or `all`. The API (`/api/storage`) measures only unless `dry_run` is sent false; the screen (`static/storage.js`) always previews the size, then asks. A project's text, plan, approvals and exports are never touched.
- After a clear, records that pointed at removed files are pruned (plan assets' `reference_images`; a character's canon, looks and source photo, which bumps its version). Refused while a job runs for that project. Folders holding files the app cannot make again (uploads, likeness, remix source, character source photo, garments) are marked and confirmed separately. Probe/test folders under `data/` can be emptied; `timings.json` is kept. Tests: `tests/test_storage.py`.

## Invariants that span files

- Canonical scene is source of truth; image prompts derive from it via `source_hash` and regenerating them never touches scene wording.
- `editorial.content_hash` defines what was approved and deliberately excludes timings, previews, issues, scene `prompts`/`adapters`, asset `reference_images`. Changing it requires migrating stored approvals and re-exporting.
- Voice is made only from a saved export whose hash equals the current plan; reference pictures are the exception (need only the registry).
- Export has `public` (spoken/shown/sent to models) and `evidence` halves; the leak gate (`story2/leak.py`) scans `public` and refuses the export on any finding. No source/author/book mentions or quotes may reach narration, prompts, or screens.
- Style is chosen once per plan (`settings.visual_style`, presets in `story2/styles.py`) and written into style asset, every scene prompt, every reference picture. Bump `DIRECTION` when the visual direction changes so old work is flagged "made for another look".
- Asset descriptions are composed from slots (`story2/describe.py`); the image models invent anything unspecified, so every person/place/prop needs concrete values. Never name a game or brand in a prompt.
- Charts, tables and documents are never drawn by an image model; `story3/graphics.py` builds them from verified facts. On-screen text is English only, 8 words max.
- People are drawn as Indian by default (`cast_indian`); a person's shoes and trousers are only written into a prompt when the shot can see them (`describe.hidden_slots`).
- Maya (`story2/maya.py`) is the default voice for new plans (plans that never chose one stay on Veena). Its emotion tags live on each sentence (`tag`), outside the content hash: the storyboard suggests one per scene (`scene.data.voice_tag`, copied to the sentences by `storyboard.apply_voice_tags`), `story2/voicetags.py` is the model's sentence-level direction (auto-run step `voicetags`), and the editor can change both on the plan screen. Keep the tag lists in `static/plan.js` equal to `maya.py` (a test checks).
- Voice engine/voice is `narrator.tts`, outside the content hash; take hashes carry the engine. Pictures and reference prompts can be redone any time (`scenes.redraw`, `refs.generate(prompts=)`) and the video lists "Changes since the last video".
- Narration is first-person Hinglish in mixed script, numbers as words; one steady emotion per voice segment.
- Voice and picture validity are tied to hashes of their inputs; changing wording/description invalidates old takes.
- Context budget: a request that would exceed `context x (1 - safety)` is refused, never truncated (`story/tokens.py`, `story/llm.py`).
- The blueprint carries a suspense plan that every beat's narration prompt receives; narration checks (`planner.make_narration`) send back repeats, stock openers, a long opening sentence and Hindi in Latin letters. Checks accept their last attempt (`JsonCaller.last_attempt`) so a run never stops on style. Compare two narrations with `python -m story2.narration_audit`.
- The finished video plays at 1.25x (`story3/video.py PLAYBACK_SPEED`); the thumbnail (`story3/thumbnail.py`) is the last auto-run step.
- A project has one story type (`story/storytypes.py`: incident, biography, documentary, explainer, listicle), copied to `plan.settings.story_type`; prompts, scoring and built cards differ by type. Plan: `docs/PLAN_story_types.md`.
- A page that blocks the plain download (403/429/503 or a bot-check page) is retried in headless Edge/Chrome (`ingest.fetch_with_fallback`); paywalls are never retried.
- A real, named person is a silhouette unless the editor confirms a public figure and approves a photo (`story3/likeness.py`): then the character sheet is painted from that photo, which is only ever a reference. Nothing is used before approval.
- Background music is optional (`story3/music.py`, off by default; long-form `plan.settings.music`, shorts `settings.music*`). The idea is planned with the story from its type and audience (auto-run stage `musicplan` after the blueprint; shorts: at the end of `planner.make_plan`): a model picks genre, one or two moods, a slow tempo and up to three common instruments from a fixed vocabulary, code keeps only vocabulary tags and adds "instrumental, no vocals", and a recipe per story type is the fallback. One quiet instrumental loop (YuE2, model `yue2-3b`, `POST /v1/audio/music`, section tags with no words, `cot` full) is made by the auto-run stage `music` (shorts: step before "Put the short together") and looped with cross-fades under the voice (`bed_from_track`, level in LUFS, ducked by `audio.mix_args`). Music is optional everywhere: a failed track never stops a run, the film uses the synthetic pad. Licence is non-commercial. Video and final hashes include the track id. Tests: `tests/test_music.py`.
- Keep checks short: run the tests for the area you changed; the full suite takes about 5 minutes.
